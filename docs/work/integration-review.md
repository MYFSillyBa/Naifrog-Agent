## 可执行发现

### [P2] 清空或关闭记忆后仍会外发主动陪伴的旧内容

位置：`src/Naifrog/Desktop/PetRuntime.cs:133–137`，关联 `src/Naifrog/SettingsWindow.cs:200,230–231`。

`recent` 遵守 RememberChat，但 `proactiveHistory` 无条件拼接到独立模型请求，并在每次成功时继续存入正文。该队列可能包含根据私人聊天生成的总结；设置页清空只调用 Chat.ClearMemory，关闭记忆只调用 Chat.ReloadMemory，二者都不处理此队列。因而一次模型陪伴提到旧私人信息之后，用户清空记忆或关闭“保留聊天记忆并用于后续对话”，下次陪伴仍会把该信息作为“此前主动发言”发给模型。该路径也不遵守 ContextPairs=0。

建议让 Runtime 统一管理记忆清空/禁用边界，清除主动陪伴缓存，并在禁用记忆时不读取或累积它；清空时提升版本或取消旧请求，避免进行中的陪伴返回后重新填入旧内容。补充注入 handler 检查：先让陪伴输出唯一标记，清空/禁用后确认后续请求不含标记。

### [P2] 多实例的普通位置保存会恢复已删除的凭据引用

位置：`src/Naifrog/Core/SettingsStore.cs:67,85–87`，关联 `src/Naifrog/App.xaml.cs:42` 的允许多实例路径。

Store 的 gate 仅保护本对象，多个实例各持有启动时的 Current。实例 A 修改 Key 后，Save 写入新凭据引用并删除旧文件；实例 B 随后拖动角色，SavePosition 从它的旧 Current 重写整个 settings.json，把 CredentialId 恢复成已经删除的引用。下次启动得到空 Key，却显示“配置已就绪”；新 Key 文件虽然仍在磁盘，但已无配置引用。B 的位置写入还会同时撤回 A 的其它配置。

**本次已复现：** 在唯一临时目录建立 A/B 两个 SettingsStore，共用配置；启用 AllowMultipleInstances；A 保存 key-before，B 加载，A 改为 key-after，再由 B SavePosition。新 Store 在 A 保存后读到 `key-after`，在 B 保存位置后输出 `key present: False` 和 `Reported status: 配置已就绪`。直接链接当前 Core 源码的临时 net9.0-windows 检查退出码 0，无网络，测试配置已清理。

建议对共享配置使用跨进程协调和版本/重读合并；位置保存只更新最新磁盘配置的位置字段。不要让仍被其它活动实例引用的凭据立即失效；缺失非空 CredentialId 对应文件时应报告凭据读取失败。仅加一个进程内锁不足以解决。

### [P2] 设置窗口的旧草稿撤回整理窗口刚保存的默认值

位置：`src/Naifrog/SettingsWindow.cs:38,228–230`，关联 `src/Naifrog/Files/OrganizerWindow.cs:278–281`。

设置窗口只在构造时克隆一次整份配置。由设置页打开整理窗口后，两个窗口可以同时存在；用户在整理窗口修改源目录、目标目录、整理方式并“保存默认值”成功，再返回设置页仅修改外观或模型并保存，旧 draft.Files 会覆盖新默认值。Save 只特别合并了最新窗口坐标，没有同步其它外部变更，也没有 Store.Changed 草稿合并。

建议记录打开/上次保存的基线，仅把实际修改的字段合并到最新配置，或者收到外部变更时刷新未编辑字段。增加同一 UI 会话中“整理保存默认值 → 设置只改不透明度 → 两边修改均保留”的检查。

### [P2] 清空记忆的磁盘失败逃逸 WPF 点击回调

位置：`src/Naifrog/SettingsWindow.cs:197–200`，关联 `src/Naifrog/Chat/ChatService.cs:121–130`。

ClearMemory 会同步调用 PersistMemory/AtomicFile；磁盘已满、文件锁定或目录权限变化时会抛异常。这个按钮直接调用它，没有像恢复默认、导出等入口那样使用 RunAction，也没有全局 DispatcherUnhandledException 处理。用户确认清空后因此可能直接终止整个桌宠；旧磁盘记忆仍存在，用户没有得到可理解的失败反馈。

建议将清空和后续刷新放在 RunAction 或明确 try/catch 内，失败时说明未能清空磁盘记忆，不显示成功。可用测试目录中锁定记忆文件的场景核对按钮错误反馈及应用继续运行。

## 其它核对与边界

- 聊天服务现在单次 Snapshot 同时获取配置与 Key；Store 先写新凭据再原子切换配置，单 Store 保存失败不会混合服务商和 Key。
- Privacy 配置改变会取消已有图像请求；启动时强制 ScreenEnabled=false；截图预览本身没有调用模型。普通外观保存不会取消普通聊天。
- 主窗口关闭链路、聊天/设置窗口取消令牌、Runtime 的 timer 和 Animator 释放均已检查。单次请求等待的结果情绪有 replyEmotionRequested 保护。
- 复核没有声称真实供应商兼容性、跨屏 DPI、完整桌面交互或断电恢复已验证；主任务正在执行真实 UI/localhost 验证。本次唯一新增运行检查是上面的多 Store 凭据丢失复现，其余发现来自明确的数据流与事件处理路径。

## 修复后的限定复审（2026-10-29）

本轮只复查前述四项及其直接修复路径，不扩展审查范围，不重复运行测试套件。已核对当前源码、`store-report.md`、`chat-report.md` 的最新补充，以及 IntegrationChecks 的对应检查。

1. **主动陪伴隐私边界：已关闭发现。** `PetRuntime.cs:96–100,140–168` 现在统一清空主动陪伴缓存并取消旧上下文令牌；记忆开关变化和 Chat.MemoryRevision 变化都会使派生缓存失效。请求结束在写入缓存前检查取消；关闭记忆时既不发送也不累积旧陪伴文本，ContextPairs=0 时不发送此前陪伴内容。`ChatService.cs:72–85,167–181,415–459` 的加密 ClearRevision 和跨实例锁使 Runtime 可以观察另一实例清空；旧聊天请求不能在清空后重新写回旧会话。
2. **多实例凭据/位置持久化：已关闭发现。** `SettingsStore.cs:60–103,192–204` 以 profile 命名互斥锁串行读写，位置保存基于最新磁盘配置，只更新坐标并一起发布对应 Key；普通保存合并变化字段。已经发布的旧加密凭据不立即删除，失败时只移除未发布的暂存凭据，因此此前 A/B 丢 Key 路径已消除。历史凭据文件保留是实现报告明确的边界，当前活动凭据仍可正常重置。
3. **设置草稿覆盖整理默认值：已关闭发现。** `SettingsWindow.cs:246–282` 在保存时以最新 Snapshot、窗口基线和编辑草稿逐字段合并，只提交用户修改；保存后更新基线并重建控件。未编辑的整理字段随最新配置保留，控件也显示最终保存值。
4. **清空异常逃逸点击处理：已关闭发现。** `SettingsWindow.cs:222` 已将 Runtime.ClearMemory 与成功反馈放入 RunAction；存储异常进入错误反馈，只有调用完成才显示成功。恢复默认入口也使用同一集中清空路径。
