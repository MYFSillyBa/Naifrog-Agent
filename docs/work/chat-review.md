# 聊天子系统复核

复核日期：2026-10-28。基于 `chat-brief.md`、`chat-report.md`、完整 `chat-review.diff`，并核对 Chat、测试和共享 Core 源码。仅静态只读复核；没有调用真实 API、重跑实现者的检查或修改实现。以下行号对应本次复核的 415 行 `ChatService.cs`。

## 结论

- **规格符合性：需修正。** 公共接口、路径兼容、自定义模型/提示词、流式累积、取消、不重试、图片隔离、加密记忆和独立请求均有对应实现；但情绪请求绕过了 `Model.ContextPairs` 的上下文限制。
- **代码质量/正确性/隐私/并发：需修正。** 请求串行化和记忆版本保护设计合理；配置与密钥不是同一个原子快照，切换服务商时存在将新密钥发给旧服务商的风险。

## 必须处理的发现

### [P1] 配置与密钥分开发布/读取，可能把新服务商密钥发送到旧地址

证据：`src/Naifrog/Chat/ChatService.cs:187` 克隆 `store.Current`，到 `:192` 才独立读取 `store.ApiKey`。相关共享实现 `src/Naifrog/Core/SettingsStore.cs:45` 先更新 `ApiKey`，`:47` 执行设置文件磁盘写入，`:48` 才替换 `Current`。Chat 的信号量并不保护 `SettingsStore.Save`。

触发条件：用户从服务商 A 切换为 B，同时有排队请求在工作线程恢复。保存已经把 Key 更新为 B，但 `Current` 仍指向 A 时，Chat 可以读到 A 的 URL 和 B 的 Key，随后在 `ChatService.cs:251–254` 将 B 的 Bearer 发往 A。即使只是把 `ApiKey` 读取移到 `Clone` 附近，Save 的磁盘写入窗口仍存在。若设置文件写入失败，密钥已更新而配置未更新的状态还可能持续存在。

建议：由共享 Store 提供单一、不可变、同时包含配置和密钥的快照，并在同一同步边界内发布；或让保存与请求快照使用同一个锁。存储失败时也不能留下服务商/Key 的混合状态。增加注入 handler 的并发切换检查，确保每次请求的 URL/Key 永远属于同一版配置，并覆盖保存失败。此修正需要主任务协调共享 Core，不应只给 Chat 加一个 Save 不参与的私有锁。

### [P2] 情绪分析忽略上下文轮数，设置为 0 时仍会外发历史

证据：`src/Naifrog/Chat/ChatService.cs:70` 取得完整已记忆历史，`:73` 只在正文请求应用 `settings.Model.ContextPairs`；`:76` 把未裁剪的历史传入分析，而 `:214–215` 固定将最近四条消息序列化发给模型，没有读取 `ContextPairs`。

触发条件：记忆开启且已有对话，启用模型情绪分析后把 `ContextPairs` 设为 0。正式回复的 messages 仅有当前消息，但其前面的情绪小请求仍包含最近两轮历史；设为 1 时同样可能多发一轮。这违反任务书“发送上下文限制 Model.ContextPairs”，也使用户选择不发送旧语境的效果不完整。

建议：情绪请求同样按 `ContextPairs` 选择完整问答对，0 时 recent 必须为空；可以进一步保留分析专用最多两轮的上限。补充开启情绪分析、预先有至少两轮历史、分别设置 0/1 的 handler 检查，验证分析请求和正文请求都遵守限制。当前 `tests/ChatChecks/Program.cs:107–140` 的上下文检查没有开启模型情绪分析，因此没有覆盖此路径。

## 已核对的积极项与验证边界

`History` 为不可变 record 的只读快照；HTTP 请求共享异步锁，排队可取消；清空/重载提升记忆版本，防止旧请求复活记忆；正文部分失败不进入保存分支；默认 handler 禁用重定向；HTTP 状态错误不带服务端正文；截图只在显式传入时进入正式请求；记忆自动保存通过 LocalVault 与 AtomicFile，导出是显式明文操作。以上均从源码核对。
